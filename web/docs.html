Quick start

tab runs on Node 22.13 or newer with no runtime dependencies. The demo brings up keys, sandbox money, a priced demo API on port 4101, a gateway on 1402, and the catalog with this site on 1403.

$ git clone <the tab repo> && cd tab
$ npm install
$ npm run demo

# then pay for something from another terminal
$ npm run cli -- fetch --agent keys/agent-claude.json --mandate keys/mandate-claude.json \
    http://127.0.0.1:1402/quote

Open the catalog to search routes, buy one from the browser with the demo's web agent, and watch receipts arrive. The test suites run in-process: npm test, npm run test:adversarial, and npm run test:evm.

For the step-by-step path that the Developers and Providers pages describe, use the commands below.

One binary, tab, for every role. During development run it as npm run cli -- …; after npm run build it is node bin/tab.js.

Protocol overview

Wire version tab/0. Three roles, four objects, all JSON. Amounts are micro-USD integers carried as decimal strings, so "10000" is one cent.

RoleHoldsDoes
OwnerThe funds and a keySigns mandates offline. Never online during a payment.
AgentIts own key and a mandateSigns one credential per paid request.
GatewayThe spec and a databaseIssues challenges, verifies, reserves, forwards, captures on 2xx.

Challenge

An unpaid request to a priced route gets a 402 with WWW-Authenticate: Tab challenge="…". The challenge names the realm, rail, recipient, amount, resource, and expiry, and carries an HMAC id so the gateway keeps no per-challenge state.

Credential

The agent retries with Authorization: Tab <credential>: the challenge, the mandate, a commitment to the request's query string and body hash, and the agent's signature over all of it. On the evm rail it also embeds the signed payment transaction.

Receipt

A successful paid response carries Tab-Receipt with the id, realm, resource, amount, currency, rail, payer, owner, recipient, a settlement reference (ledger:<hold> or evm:<tx hash>), and a timestamp. A non-2xx upstream answer is passed through with Tab-Void instead, and nothing is charged.

Refusals

Every refusal is a fresh 402 carrying an RFC 9457 problem with type: urn:tab:problem:<code> and a fresh challenge. Codes: payment-required, malformed-credential, invalid-challenge, payment-expired, verification-failed, mandate-invalid, mandate-denied, mandate-exceeded, insufficient-funds; plus not-found (404) and upstream-failed (502). Clients retry exactly once.

Mandates

A mandate is the signed spending limit. The owner issues it once; the agent carries it in every credential; the gateway enforces it on every request. It is not secret, but it grants spending.

FieldMeaning
ownerWallet id that signs, and whose funds move.
agentWallet id allowed to spend under it.
budgetMicro-USD the agent may spend in the window.
windowtotal for the mandate's lifetime, or day per UTC calendar day.
max_per_callCeiling on one request, or null.
allowRealm globs. ["*"] means any gateway.
issued_at, expires_atISO 8601. Expired mandates are refused.
evm_ownerThe owner's 0x account, attested by the signature. Required on the evm rail so payments can only draw on this owner's allowance.
id, sigSHA-256 of the canonical body, and the owner's Ed25519 signature over it.

Paste a mandate into the catalog's verifier to check its signature and see its terms in plain words.

Verification order

The gateway checks a credential in exactly this order. Each failure is a fresh 402 with the reason named.

  1. Parse the credentialWrong shape → malformed-credential.
  2. Challenge authenticity and relevanceThe HMAC id must verify, and realm, rail, recipient, amount and resource must match what this request would cost → invalid-challenge. Expired → payment-expired.
  3. Mandate validity and agent bindingStructure, id, owner signature, expiry → mandate-invalid. The credential's agent must be the mandate's agent and the signature must cover the request → verification-failed.
  4. Request commitmentThe query string and the SHA-256 of the body actually received must equal what the agent signed.
  5. Realm allow-listThe gateway's realm must match a mandate glob → mandate-denied.
  6. One database transactionBurn the challenge id (a duplicate is refused), check the per-call cap and the window budget → mandate-exceeded, then reserve on the rail → insufficient-funds. On evm, the embedded transaction's every field must match the challenge, and its hash must be unused.
  7. Forward, then captureUnreachable upstream → 502, nothing charged. Non-2xx → Tab-Void. Only on 2xx does money move.

Rails

A rail is how money settles. Each gateway uses one, set in its spec, and challenges name it so an agent knows what it is signing.

ledger

Sandbox balances in the gateway's SQLite file, funded with tab mint. Free, instant, and the default. Receipts reference ledger:<hold id>.

evm: USDC on Robinhood Chain

The owner approves the agent as a spender of their USDC with tab evm approve. Each payment is a transfer transaction the agent builds from the challenge and signs itself; the gateway checks every field, dry-runs it, forwards upstream, and broadcasts only on 2xx. The gateway holds no payment key. Receipts reference evm:<tx hash>, and the gateway's rail_info.explorer tells front ends where to show it.

Gateway HTTP surface

Besides the priced routes themselves, a gateway serves a small discovery surface. Every JSON endpoint sends Access-Control-Allow-Origin: *.

PathReturns
GET /.well-known/tabRealm, rail, recipient, rail info, and the full service and route list with prices.
GET /.well-known/tab/wallet/<id>Available balance for a wallet on this gateway's rail.
GET /.well-known/tab/receipts?limit=The last 200 receipts, only if the spec sets public_receipts.
GET /.well-known/tab/evm/nonce/<0x>The pending nonce for an account, so agents need no RPC of their own. evm rail only.

Unlisted paths are 404 and never proxied. Routes priced "0" are forwarded unpaid.

Catalog API

The catalog is discovery, not part of the payment protocol. It polls announced gateways, indexes their routes, and serves this site.

PathDoes
GET /v1/catalog.jsonEvery known gateway with its status, rail, and routes.
GET /v1/search?q=Search routes by name, path and description. Empty query lists all.
POST /v1/announceRegister a gateway origin. Private origins are refused unless the catalog runs with --allow-private-origins.
POST /v1/refreshRe-read every gateway now.
POST /v1/mandate/verifyCheck a mandate's structure and signature, optionally against a realm.
GET /v1/wallet?origin=&wallet=Ask a gateway for a wallet's available balance.
GET /v1/receipts?limit=Recent receipts across gateways that publish them.
GET, POST /v1/tryWhether the catalog has a web agent, and a paid request made with it. Anyone who can reach the catalog can spend that agent's limit.

Deployment

The operator's manual takes a clean VPS to a running gateway, catalog and site behind nginx with TLS. The shape is:

  1. Install and buildNode 22.13+, npm install, npm run build. Keep web/ next to dist/.
  2. Write the spec and keysOwner and agent keys, a mandate, and spec.json for each upstream you front.
  3. Run the gateway and catalogAs systemd services on loopback, ports 1402 and 1403, with database files you back up.
  4. Proxy with TLSnginx or Caddy in front, passing the host and the Authorization header through.
  5. Go to real moneySwitch the spec to the evm rail, approve the agent's allowance, fund it with gas, and run the security checklist.

All servers bind to every interface by default. Firewall them or bind to loopback before exposing a machine.
