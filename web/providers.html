Get started
Providers

Price your API. Get paid per request.

Put tab in front of any HTTP API. Describe your routes and prices in one JSON file. Agents pay before you answer, and you never build a billing system.

One file describes your prices.

A spec names your gateway (its realm), says who gets paid, and lists your services. Each service points at your existing upstream and lists priced routes.

Prices are USD strings. A price of "0" is forwarded free. Paths may have parameters like /v1/things/:id. Anything not listed is not proxied.

realm
Your gateway's name. Owners allow-list realms in their limits.
recipient
The wallet that receives payments.
prefix
Mounts a service under a path. Empty for the root.
upstream
Where tab forwards paid requests.
upstream_headers
Headers tab injects, such as your real API key. Callers never see them.
public_receipts
Publish the last 200 receipts for the catalog's live feed.
// spec.json
{
  "realm": "lingua.example",
  "recipient": "<your wallet id>",
  "public_receipts": true,
  "services": [
    {
      "name": "Translation API",
      "prefix": "",
      "upstream": "http://127.0.0.1:8080",
      "upstream_headers": { "X-Api-Key": "${LINGUA_KEY}" },
      "description": "High quality translation, 40 languages",
      "routes": [
        { "method": "POST", "path": "/v1/translate", "price": "0.004",
          "description": "Translate text" },
        { "method": "GET",  "path": "/v1/languages", "price": "0",
          "description": "Supported languages" }
      ]
    }
  ]
}

Start the gateway.

The gateway is one process in front of your API. It answers unpaid requests with a price, verifies payments, forwards paid requests upstream, and settles only when you answered successfully.

Announce it to a catalog and agents can find your routes by searching. The catalog reads your gateway's own service list, so it stays in sync with your spec.

$ tab serve --spec spec.json --port 1402 \
    --origin https://pay.lingua.example \
    --announce https://catalog.example.com

# what agents see, straight from your gateway
$ curl https://pay.lingua.example/.well-known/tab
{ "realm": "lingua.example", "rail": "ledger", "services": [ … ] }

Behind nginx or Caddy with TLS in production. The deployment guide covers the full setup.

What happens to each request.

Your API sees only paid requests, with three extra headers telling you who paid. The buyer's payment header is stripped and your configured upstream headers are injected.

You are paid when you answer with a 2xx. If your API fails or is unreachable, the reservation is released and the caller is not charged. The failure mode is always in the buyer's favor, which is what makes agents willing to pay up front.

  1. Unpaid requestAnswered with 402, the price, and a challenge. Nothing reaches your API.
  2. Paid requestSignature, limit, and funds are verified. The amount is reserved.
  3. Forwarded to youWith Tab-Payer, Tab-Owner and Tab-Hold headers for attribution.
  4. You answer 2xxThe payment settles. The response carries a signed receipt.
  5. You answer anything elsePassed through with Tab-Void. The reservation is released, nothing charged.

How you get paid.

Every gateway settles on one rail. Start on the sandbox ledger while you integrate, then switch the spec to real value.

On Robinhood Chain, payments are USDC transfers from the owner's wallet to yours, one per request, broadcast only after you answered. The gateway holds no payment key. Receipts carry the transaction hash, and the explorer link shows in the catalog.

Sandbox
"rail": "ledger", or omit. Balances live in the gateway's SQLite file.
Real value
"rail": "evm" with the block on the right.
Chain
Robinhood Chain testnet, chain id 46630.

Before real money.

  • Serve behind TLS, and bind the gateway to loopback so only the proxy reaches it.
  • Keep spec.json private if it carries upstream API keys. Use environment variables for them.
  • Back up the gateway's database file. It holds balances on the ledger rail and the record of every hold.
  • Turn on public_receipts only if you are happy to expose payer and owner wallet ids.
